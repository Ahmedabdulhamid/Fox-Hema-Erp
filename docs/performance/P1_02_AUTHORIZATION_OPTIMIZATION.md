# P1-02 Authorization Optimization Results

## Summary

P1-02 confirmed two redundant Sales Orders location checks. `SalesAccess` had a private request-fact key for branch membership instead of using the shared `RequestAuthorizationFacts::actorHasLocation()` fact used by `LocationContext`. It also used a different key for an active scoped branch than for an active target branch. Both pairs therefore issued the same query twice in the same request.

The change reuses those existing request facts. It reduces Sales Orders by two SQL executions per request in the synthetic profile: GET fell from 20 to 18 queries and Livewire refresh from 19 to 17. The two duplicate fingerprints disappeared. No policy, Gate result, ownership decision, or permission result is cached. All existing invalidation and transaction behavior is retained.

The measured wall-time changes are not presented as a speedup: several unrelated pages also changed substantially between profiling runs, and the synthetic fixture has broad timing variance. Query reduction is confirmed; causal request-latency improvement is not.

## Environment and methodology

- Runtime and fixture: PHP 8.5.5, Laravel 13.35.0, MariaDB 10.4.32; same focused `GlobalQueryOptimizationTest::test_profile_p1_01_representative_pages_in_three_runs` and one-record synthetic dataset used for P1-01.
- Before values are the three-sample P1-01 results in [P1_01_MEASUREMENTS.md](./P1_01_MEASUREMENTS.md). After values are three new samples for each of the same nine pages, with both initial GET and Livewire refresh where supported (54 requests). They used the same actor, permission set, branch, route, fixture shape, cache setup, and test-kernel methodology.
- Before and after used random `codex_public_ids_test_treasury_*` schemas generated by `tests/Support/TreasuryDatabaseBootstrap.php`. Before each test connection, the dedicated MariaDB listener was verified on `127.0.0.1:33316`; its process used `storage/framework/testing/pos-mariadb/my.ini` and the isolated test data directory. `tests/Concerns/RefreshDatabase.php` additionally refuses non-testing or non-prefixed MySQL schemas. The bootstrap creates and drops only its generated schema.
- The application-configured database was not contacted; no `e_commerce` schema or shared Redis was used. `ReadModelCache` used the isolated `array` store. Debugbar was disabled for every sample; no persistent configuration was changed.
- All 54 after requests returned HTTP 200 at database transaction level zero. Wall time is Laravel test-kernel duration, not browser/network latency. SQL time is the sum of `QueryExecuted` timings; peak memory is PHP's allocator peak. Authorization SQL counts use application stack attribution. The profiler retains the first source stack for identical SQL text, so source attribution is indicative rather than a complete call counter.
- Durations in the table are before median → after median (after minimum–maximum). Full before ranges are retained in P1-01. Query counts, duplicate executions, and stack-attributed authorization counts were stable across the three samples. Memory is before → after peak MiB (after range).

## Authorization fact and invalidation measurements

There is no production hit/miss counter in `RequestAuthorizationFacts`; the request-wide figures above are measured SQL counts attributed to authorization call stacks, not invented memory-cache statistics. Focused test probes counted resolver calls and SQL executions directly:

| Scenario | Before change | After change | Result |
|---|---|---|---|
| Sales branch membership / active-scope checks | Two membership SQL executions and two identical active-branch SQL executions across `LocationContext` plus two Sales authorization checks | One membership query and one active-branch query | Shared membership now uses `actorHasLocation`; both active branch call sites use the same request-fact key. Direct probe and page profile agree that both duplicate fingerprints are gone. |
| Unrelated write (`UPDATE brands`) | Three membership fact calls: 2 misses/SQL executions, 1 hit; one unrelated DML invalidation | Unchanged: 2 SQL executions, 1 hit, 2 misses, 1 invalidation | Confirms current global DML invalidation is unnecessarily broad in this case. It was intentionally not narrowed because arbitrary SQL, database triggers, and indirect writes cannot be safely ruled out across the application. |
| Read-only nested transaction wrapped by `duringReadTransaction` | Four fact calls: 3 resolver misses and 1 hit; 0 transaction-event invalidations | Unchanged | Request facts are deliberately not memoized at a transaction level different from the request's initial level. This avoids reusing facts produced inside a transaction after rollback. |
| Normal GET / Livewire | 5–10 stack-attributed authorization SQL executions per request in P1-01 | 5–10 across pages; Sales Orders 10 → 8 | Only the two confirmed duplicate Sales queries were removed. |

### Invalidation behavior retained

Static inspection of the current provider and focused tests establish the following behavior:

- The SQL listener ignores read statements (`SELECT`, `SHOW`, `EXPLAIN`, `DESCRIBE`, `PRAGMA`) and writes to the configured session, database cache, and cache-lock tables. Other non-read statements call `RequestAuthorizationFacts::forget()`. DML preserves schema metadata; other statements mark schema metadata stale.
- Transaction begin, commit, and rollback events invalidate request facts, except while `duringReadTransaction()` is active. Facts are not memoized while the live transaction level differs from the level captured at request start. A write inside a transaction still reaches the SQL listener and invalidates facts.
- Permission/role grants and revocations, module activation or mapping changes, user activation, and branch membership/location changes remain visible during the request. Permission team, database/PDO, actor, and request boundaries remain in the existing fact scopes.
- Database cache writes do not invalidate request facts. Focused tests also verify Livewire permission revocation and financial authorization after a posting permission is revoked.

No invalidation rules, transaction handling, `ReadModelCache`, authorization service architecture, or business logic were changed.

## Focused security regression results

`tests/Feature/SharedAuthorizationPerformanceTest.php` passed on the isolated MySQL/MariaDB bootstrap: **23 tests, 145 assertions**. Coverage includes direct and role permission grants/revocations, module activation/mapping changes, active user changes, branch membership removal and cross-branch denial, team switching, different users across requests, rollback/commit boundaries, nested transactions, unrelated writes, location deactivation, financial posting authorization after revocation, and real Filament/Livewire revocation.

The P1-01 representative-page profiler passed after the change: **1 test, 75 assertions, 54 measured requests**. No full PHPUnit suite was run.

## Ranked confirmed findings

1. **Inventory Overview query volume and repeats — unchanged.** It remains at 33 GET / 31 Livewire SQL executions with three exact repeated fingerprints. P1-01 attributed repeated product presentation work to `InventoryProductPresentation`; this remains the largest measured query-volume target in the fixture.
2. **Shared authorization SQL across pages — confirmed, partly necessary.** Stack-attributed authorization work remains 5–9 queries per request after P1-02 (5–10 before). Only the Sales location duplicates were proven redundant; other checks still run their policies and have not been removed.
3. **Sales Orders duplicate location authorization — fixed.** Two repeated fingerprints per request became zero; SQL query count fell by two. This is a query-count improvement, not a measured browser or production latency claim.
4. **POS Terminal cold GET volume — unchanged.** It remains at 33 GET queries (14 on Livewire), one repeated fingerprint, and two ReadModelCache epoch SQL statements on the cold GET.
5. **Non-SQL test-kernel time and timing variance — measured, cause unconfirmed.** Products, Treasury, and Access Management still show substantial wall time beyond SQL duration. Rendering and middleware were not separately timed, so no single cause is confirmed.

## Risks and unresolved limitations

- The fixture is small and synthetic; it does not establish production latency, realistic data cardinality, or concurrency behavior.
- Debugbar enabled/disabled A/B, Redis latency, and isolated multi-worker behavior were not measured. The test cache was `array`; no shared Redis namespace was available or touched.
- Wall-time and SQL-time ranges are broad, and unrelated pages changed between runs. Do not interpret their lower or higher medians as effects of this Sales-only change.
- Global DML and transaction invalidation remain conservative. The unrelated `brands` write probe confirms an avoidable invalidation, but narrowing it safely requires trigger-aware, connection-aware invalidation coverage beyond this task.
- Read-only transaction memoization remains disabled at changed transaction depth. Improving it safely would require explicit handling of writes and rollback after facts are resolved inside the transaction.
- Hit/miss counts for full page requests are not available without adding persistent runtime instrumentation; the report limits exact cache-hit/miss counts to focused probes and reports SQL attribution separately.
- A second database connection pointing at a separate disposable schema was not configured for this test run. Existing connection-identity guards were left untouched.

## Recommendation for P1-03

Proceed with the planned **ReadModelCache version/payload measurement** in an isolated Redis namespace. The current fixture confirms cold-request database epoch work (1–4 statements on several pages) but does not measure Redis behavior or prove that changing version initialization is safe. Measure first use, warm hits, invalidation, rollback, and concurrent workers before proposing any cache architecture change.
