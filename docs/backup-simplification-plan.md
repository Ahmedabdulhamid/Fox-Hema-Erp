# BackupRestore simplification and completion plan

2026-11-14. Planning only: application code, databases, credentials and execution gates are unchanged. No tests, migrations, backups, restores or remote operations were run. Review covered BackupRestore, its direct integration references and existing finalization/readiness evidence; no unrelated ERP audit.

**Recommendation:** retain the archive/transport/recovery implementation; retire application-wide admission only through a controlled replacement. Prefer one bounded maintenance-window runner over a new supervised backup queue. Exclusive capture is not currently established. Complete authorized archive download independently while capture stays blocked.

## Minimum viable capture architecture

Use a **single bounded local maintenance runner** that claims existing operation ownership, establishes exclusive capture, invokes the existing dump/file capture, and then releases maintenance before encryption/upload/readback. Manual requests and schedule occurrences use the same runner; neither needs an ordinary long-lived worker for capture. Reuse existing run/occurrence records, not a new job platform. Keep restore delivery separate and operation-compatible.

Required sequence:

1. Prevent new writers and restarts through an independently controlled maintenance facility: web/POS/Livewire ingress, console tasks, ordinary workers and restart sources. Laravel maintenance mode is only the user-facing response. Do not rely on the old admission flag.
2. Drain existing work, including transactions and schema operations; verify completion/rollback and worker/child exit through the controlling facility. Unknown work blocks capture. Heartbeat age, an empty queue or one quiet process-list query cannot prove completion.
3. Exclude external database DML/DDL, privileged scripts and database events, and all writers to captured filesystem roots. The facility must control relevant database access and filesystem principals, including restart/reconnect behavior; a general database read-only setting or an advisory application lock alone is insufficient. Verify that the capture/metadata principal has only reviewed exceptions. No service-account or ACL changes are authorized by this plan.
4. Keep source database/schema and media stable from before reference/dump inspection until the final file copy/hash check. This makes sequential dump and media capture coherent. Continue existing schema/trigger/reference/hash validation. Preserve honest exclusions such as offline POS client queues.
5. On interruption or lost proof, fail/quarantine the attempt and keep external exclusion held. Never publish available status or automatically replay an ambiguous attempt. Cleanup/resume requires exact operation ownership and independent proof that capture processes/descendants have stopped; expiry alone is insufficient.
6. Resume only the exact services/access state suspended by this operation, after stable private staging and capture-stop proof. Encryption/cloud failure after safe resume marks the artifact attempt failed; it does not require reopening capture or deleting source data. Retain cleanup markers and existing upload-abort ownership checks.

**Minimum missing operational prerequisite:** one available, independently enforced exclusive maintenance capability covering database/schema/media access and writer restart sources, remaining closed on runner failure. None is proven on this Windows workstation. Do not build a generic watchdog/containment system to manufacture that prerequisite. If unavailable, leave capture blocked; automatic backups additionally require that capability to operate unattended and repeatably. An operator-only shutdown cannot satisfy scheduling.

## Three implementation milestones

### 1. Safe cleanup and simplification — 2–3 developer days, conditional

- Change `Providers/BackupRestoreServiceProvider.php`, `bootstrap/app.php`, `Services/BackupCoordinator.php`, the four readiness/monitoring services above, `Filament/Pages/BackupHistory.php` and its history view. Remove direct admission calls only in `app/Modules/Products/Services/ProductImageManager.php`; replace CoordinatedFileUpload in `app/Modules/Products/Filament/Resources/Brands/Schemas/BrandForm.php` without changing business behavior.
- First preserve an unconditional blocked default using UnavailableCaptureProtection. Before detaching guards, separately verify gates disabled and no active/unresolved barrier, writer, backup or recovery ownership. If proof is unavailable, do not detach them. Then remove the conditional candidates and their provider registrations/references together. This staged cleanup must not make execution possible.
- Only with the maintenance prerequisite, add `Services/MaintenanceCaptureProtection.php` and `Console/RunMaintenanceBackup.php` at the existing seam; adapt coordinator, CreateFullBackup, ScheduledBackups and RunBackupAutomation for bounded execution. No assertion-file or configuration-only success path. Retain run leases, manual/schedule idempotency and guarded legacy-job refusal.
- Acceptance: normal ERP hooks no longer depend on backup admission where removed; capture stays rejected without independent proof; known interruption stays quarantined; manual/scheduled delivery cannot bypass ownership. Financial triggers, transactions and authorization remain unchanged.
- Focused tests: new maintenance acceptance/refusal/loss-of-proof tests, exact owner/resume tests, existing coordinator overlap/recovery tests; narrow product-media and HTTP termination regressions for removed direct hooks. Replace obsolete admission tests with equivalent capture guarantees, not blanket deletion of mixed safety suites.
- Blockers: state verification before removal; independent maintenance capability before execution integration. Defer physical table drops; they are unnecessary for completion.

### 2. Complete user-facing functionality — 1–2 developer days

- Add `app/Http/Controllers/DownloadBackupArchiveController.php` and module `Services/BackupDownload.php`; register an authenticated named route in `routes/web.php`. Extend `Services/BackupPermissions.php` with `backups.download`, `Policies/BackupRunPolicy.php`, history page/view and `lang/{ar,en}/backup_restore.php`. The direct registration consumer is `app/Modules/AccessManagement/Services/ModuleRegistry.php:103`; reuse it, without granting export rights implicitly or mutating active assignments.
- Authorize active user/module/global permission at the backend, require available/verified/nondeleted run and stable destination/artifact identity, download encrypted bytes privately through BackupTransport, verify full size/checksum **before** serving, and use safe attachment/no-store headers. Never send plaintext keys, arbitrary object keys or public R2 URLs. Handle disconnect/error cleanup and abandoned temporary files using bounded ownership-checked cleanup; coordinate downloads with deletion so a concurrent deletion cannot yield a partial response.
- Keep manual/schedule/restore controls honest about readiness, with bilingual blocked/success/failure messages. Retain R2 settings, history and RestoreCenter. Retention and notification delivery stay off.
- Acceptance/tests: authorized exact-byte encrypted download; unauthenticated, view-only, location-only, revoked, inactive-module and cross-run substitution denied; corruption/truncation fails before response; private temporary cleanup; existing scheduling occurrence/DST/idempotency and restore authorization tests only where affected.
- Dependency: download can be implemented immediately using synthetic artifacts/fake transport, independently of milestone 1 capture readiness. Real capture/scheduling remains blocked.

### 3. Focused end-to-end verification — 1–2 developer days

- Dependencies: maintenance proof for capture acceptance; milestone 2 for download; explicit later authorization for any real R2 or operational backup/recovery trial. Local tests cannot approve those trials automatically.
